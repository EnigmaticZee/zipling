Inside Arca.

No magic codec exists. zstd and LZMA are within a few percent of what their kind can do, and anyone promising ten times better is selling something or losing data. Arca wins somewhere else: in what reaches the codec.

01 · The premise

Mainstream archivers see noise. Arca sees files.

ZIP and 7z treat a JPEG, a PDF or a Mac app as opaque bytes. Most of what is inside is already compressed, badly or in a way the codec cannot see through. Arca undoes that first, reversibly, and compresses what is really there.

02 · The pipeline

One file at a time, on every core.

There are no batches. Every file is its own task, the packer takes results in a fixed order so the archive is deterministic, and blocks start compressing the moment they fill. One slow file never idles the other cores, and there is no compression tail at the end.

Sniff

Magic bytes, never extensions. Known-compressed media goes straight to store, at zero CPU.

Transform

JPEG, Deflate, arm64, PNG, DMG: undone, then proved by its inverse.

Hash & dedup

A keyed hash of the content. The first task to hash it claims it; duplicates skip the work.

Lanes

Text, binary, image, code, store. Each chunk routed by a probe, not by the file's name.

Blocks

Solid blocks, compressed independently and in parallel as they fill.

Write

One streaming pass. The index comes last, so opening a 100 GB archive reads only the end.

Each one measured on the same data as the benchmarks, and each one in the research log with the numbers that got it in.

01 · JPEG coefficient coder

Photos, 30% smaller, bit for bit.

A JPEG is a grid of frequency coefficients coded with Huffman tables from 1992. Arca reads the coefficients and codes them again with a static model fitted to each image and four interleaved rANS streams, then decodes the result and compares it with the original before keeping it. The photo comes back identical to the byte.

  • −2.7%against Dropbox's Lepton on the photo set, the previous best
  • 1.7×faster to extract than Lepton
  • every onedecoded and compared before it is kept
  • Leptonstays as the fallback for progressive JPEGs and synthetic textures

02 · The one number inside macOS

macOS's own compressor, replayed exactly.

Mac apps carry asset catalogs and disk images compressed with LZFSE, Apple's codec. Apple's open-source lzfse 1.0 re-created only 66 of the 193 chunks in a test image. Laying the two token streams side by side showed every difference began where macOS flushed a short pending match early. One threshold changed, 3 × 315 waiting literals instead of 8 × 315, and all 193 chunks came back identical. Each stored stream records which value re-creates it.

  • 127 / 193chunks lzfse 1.0 got wrong out of the box
  • 1number changed in the encoder, two lines of code
  • 193 / 193chunks re-created byte for byte afterwards

03 · Disk images

Taken apart, compressed properly, rebuilt.

A DMG is hundreds of chunks, each compressed with zlib, bzip2, LZMA or LZFSE at whatever level its maker chose. Arca expands every chunk it can re-create, compresses the raw data with modern codecs, and rebuilds the image byte for byte on extraction. For the zlib level 9 chunks that installers favour, a re-implementation of zlib's match search finds the same answer without walking the whole hash chain, so replaying them no longer costs more than it saves.

  • 4chunk codecs replayed: zlib, bzip2, LZMA and LZFSE
  • 485 / 485chunks of a 500 MB installer image rebuilt exactly
  • a budgeton rebuild time, so a stubborn image is stored as it is, never stalled on

04 · PNG pixel codec

Pixels predicted, not matched.

Inside a PNG are rows of filtered pixels. At Max and Ultra*, Arca undoes the filters, predicts each pixel from its neighbours and codes only the surprise with an adaptive binary coder. On the benchmark's PDFs and screenshots it lands within 0.3% of xz at its strongest, for a seventh of the processor time.

  • 70.62 MBArca, 22.3 s of CPU
  • 70.44 MBxz −9 on the filtered rows, 167.8 s of CPU
  • 7.5×less processor time for the same size

05 · The Max lane

Text sorted before it is coded.

At Max, text and code go through a Burrows–Wheeler transform (libbsc) instead of LZMA: the data is sorted by context so the same letters sit together and code in a few bits each. On the Silesia text block it is 19% smaller than LZMA2's strongest setting and 18 times faster to make. Binaries stay with LZMA, where the transform loses. Default borrows the same lane for static libraries and executables, with its own zstd as the fallback where the transform does not pay: source trees 15% smaller at no cost in time.

  • −19%on Silesia text against LZMA2 with 273-byte matches
  • 18×faster to make, per block
  • 22.7 → 1.6 ssource trees at Max
  • +31%on Mach-O binaries, so those keep LZMA

06 · Verified before accepted

A transform bug can cost ratio. Never data.

Every forward transform is followed by its inverse and a byte comparison before the result is kept; anything that does not come back identical is stored as it was. Every block carries a keyed hash of its compressed and its decoded bytes, under a random key drawn for each archive, and nothing is written until the block holding it has passed both checks.

  • 2 hashesper block: the compressed bytes and the decoded bytes
  • 2¹²⁸keyed POLYVAL, a fresh random key per archive, so a false duplicate match is bounded
  • BLAKE3on the index, which holds the key
  • 0 byteswritten before both checks pass
1.3–1.45× fasterliblzma's strongest blocks, from two speed patches that leave every output byte unchanged.
zlib, exacta level 9 match search that returns the same newest, longest string without walking 60 chain steps per lookup.
clones, not copiesduplicates come back as APFS clones on extraction: instant, and no extra disk space.
a graph, not wavesextraction takes the best ready item from one priority queue: blocks first, then the costliest work, so nothing long starts last.

05 · Ours and borrowed

What Arca adds, and what it stands on.

The honest premise cuts both ways. Nothing here is a brand-new theory of compression, and several of the parts are the best open-source work in their field, used as they are. What is new is what was built around them.

Built here

Arca's own

  • The pipeline and the format. File tasks on every core, lanes, content-defined dedup, parallel solid blocks, a footer-last layout that opens a 100 GB archive by reading its end.
  • The JPEG coefficient coder. Static model per image, four rANS streams, smaller and faster than Lepton.
  • The PNG pixel codec. Prediction and an adaptive binary coder at a seventh of xz's CPU.
  • The LZFSE replay. The one setting that makes Apple's encoder re-create what macOS writes.
  • Disk images, expanded and rebuilt. Four chunk codecs, a rebuild budget, and an exact faster search for zlib level 9.
  • The liblzma speed patches. 1.3 to 1.45 times faster, identical output.
  • The extraction scheduler. One priority queue, blocks first, duplicates as APFS clones.
  • Verification at every step. Inverse-and-compare for transforms, two keyed hashes per block, BLAKE3 on the index.
Borrowed, with thanks

Standing on

  • zstd for the Fast and Default lanes.
  • liblzma (XZ Utils) for binaries at Max and Ultra*.
  • libbsc and libsais for the Burrows–Wheeler lane.
  • Lepton as the JPEG fallback.
  • preflate to expand Deflate streams and record the diff that re-creates them.
  • lzfse, Apple's reference encoder, with the one setting changed.
  • zlib with the exact fast search added.
  • PPMd, kept available as a text codec.
  • BLAKE3, POLYVAL and FastCDC for hashing and chunking.
